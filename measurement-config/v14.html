Structure and data model

A workflow holds an ordered list of steps. A step is a group of measurements the inspector performs together, and it renders as one table in the inspection report. A step holds an ordered list of values — each value is a column of that table.

step = { name, mc, values[] } value = { name, recordedAt, required, specification, unit, source, evaluation }

Measurement Chart — the one structural field

mc is either nothing or a set of chart types. Those are different configurations: “no chart” and “a chart of any type” cannot share one representation, which is why it is nullable rather than an empty list. Its presence is what gives the step a POM level — there is no separate flag that could fall out of step with it.

A Measurement Chart is a group of POMs. It carries no unit — each POM inside it carries its own unit, standard value and tolerance bands. Selecting a chart means measuring every POM in it.

Levels — how many cells a value has

Every value says where it is recorded. The same three levels have the same shape in every domain; only the vocabulary differs, and the vocabulary is the client’s.

Lot — once for the whole lot.garment: order line · fabric: dye lot
Sample — once per sampled unit.garment: piece · fabric: roll
POM — once per point of measure.the only level a chart step has

The chart decides which levels the step offers. With a chart, POM is the only one — the step’s table is the chart, so every column in it is a column of that table. Without a chart, lot and sample are both available and a step may mix them: a moisture check records a reading per sample beside a single air temperature for the lot.

No count on this screen is knowable

The POM list resolves from the chart attached to the item being inspected. The sample count is derived from lot size upstream. So a value says per sample and never how many, and the preview shows the fan without inventing a number.

Grain, and references between levels

A value’s grain is the set of levels it varies over, derived from where it is recorded. When one value feeds another, the two grains decide what the reference means:

  • Coarser feeding finer broadcasts. A lot-level value applies to every sample under it. Well defined, nothing to state.
  • Finer feeding coarser needs a named aggregate — average, lowest, highest or total. Without one the reference is ambiguous: which sample’s value? The formula editor will not save until it is named.

Each of those four is defined for any number of cells, including none. That is the bar: an aggregate whose meaning depends on exactly one cell being filled is not an aggregate, it is an unenforceable assumption about data entry — and a config screen must not encode a rule it cannot enforce.

There is no first or last either. Positional selection needs an ordered axis, and samples are a random draw from the lot, so “sample 1” says nothing “sample 3” would not. The one genuinely ordered thing, a wash sequence, is modelled as separate columns, so a formula names the column rather than a position.

Note what this means for a destructive test. Shrinkage and colourfastness destroy the swatch, so one unit per lot is tested — but the value is then a property of the lot, and that is the level it is recorded at. The unit the swatch came from is provenance, not a measurement axis. Modelling it per sample and reducing it back up needs exactly the kind of aggregate this screen refuses to offer.

Specification — where the criteria come from

A value recorded per POM may take its unit, standard value and tolerance from that POM, or have them defined here. This is declared, not inferred: whether a given quantity is configured as a POM is a client’s choice, not a property of the quantity, so the same measurement is POM-backed for one customer and hand-defined for another. A calculated value is always defined here — a derived number is not the POM’s measurement, so it cannot inherit the POM’s standard.

Source — entered or calculated

Either the inspector types it, or a formula computes it. A formula names other values in the same step; a custom expression binds as many of them as it needs to letters and refers to them by letter. A calculated value may carry no evaluation at all, which is how an intermediate figure feeds another formula without being judged itself.

Evaluation — one structure, several presets

evaluation = { mode: rule | inspector | none, rule: { source, preset, standard, basis, bands[], fallback } } band = { lower: {value, inclusive}, upper: {value, inclusive}, outcome }

Every rule reduces to bands on a number line. preset records what the admin meant — “≥ 5” and “range 5 to unbounded” evaluate identically but must reopen as what was picked — while evaluation itself reads only the bands and the fallback. Bands are checked in order, first match wins, so they may nest or sit side by side; a band is only broken when an earlier one already covers all of it.

A standard value present means the bands are read relative to it, as a percentage or a difference. Absent, they are actual values on the measurement scale. There is no third option. One rule governs every cell of the column.

Drag the handle on a row to reorder it. Formulas reference other values by name, so order never affects which value feeds a formula — it is only for reading top to bottom.
