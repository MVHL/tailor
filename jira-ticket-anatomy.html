Problem Framing
WHYProblem Statement(s)

One or more pain points or opportunities. Each states who is affected and what the impact is. Every requirement must trace back to a problem here — problems with no matching requirement go in Non-Goals.

Example
  • P1
    Customers can't apply more than one discount code — 12% of orders are abandoned at checkout; support receives ~80 tickets/week.
  • P2
    When a discount code fails, the error is generic ("Invalid code") — users can't tell if it's expired, incompatible, or mistyped.
▼
WHATRequirements

User-facing outcomes. Each traces to one or more Problems. One requirement can address multiple problems simultaneously.

Example
  • R1
    Users can enter and apply up to 3 discount codes per order
    solvesP1
  • R2
    Each code is validated in real-time (<1 s) before checkout proceeds
    solvesP1
  • R3
    Incompatible codes show a specific conflict message
    solvesP1P2
  • R4
    Expired codes display the expiry date in the error
    solvesP2
Won't DoNon-Goals

Work acknowledged but explicitly excluded here. Naming it prevents scope creep; deferred work links forward to a follow-up ticket. Non-goals sit outside the trace — nothing below depends on them.

Example
  • NG1
    Admin UI for creating or managing discount codes
  • NG2
    Stacking logic for %-off + $-off combinations
    deferred to→ SHOP-241

Done MeansAcceptance Criteria

Observable, testable conditions. Each AC traces to one or more Requirements — together they must cover every requirement with no gaps.

Example
  • AC1
    Up to 3 valid codes applied; total reflects combined discounts.
    coversR1
  • AC2
    A 4th code is blocked; UI shows "Maximum 3 codes reached."
    coversR1
  • AC3
    Single-code validation completes in under 1 s under normal load.
    coversR1R2
  • AC4
    Incompatible codes show: "Code X cannot be combined with Code Y."
    coversR3
  • AC5
    Expired code shows: "This code expired on [date]."
    coversR4

Test Plan

Written by QA or developer from the AC directly. Specific scenarios covering happy paths, edge cases, failure modes. Can start as soon as AC is final — no code needed yet.

Example
  • T1
    [Happy] 3 valid codes → all applied, total correct.
    coversAC1
  • T2
    [Limit] 4th code attempted → blocked, message shown.
    coversAC2
  • T3
    [Perf] Validation under load → under 1 s.
    coversAC3
  • T4
    [Error] Two incompatible codes → specific conflict message.
    coversAC4
  • T5
    [Error] Expired code → expiry date in error.
    coversAC5
  • T6
    [Edge] Invalid code → clear error, no crash.
    coversAC1AC3

✕ Don't Dump These in the Body

None of these are forbidden from the ticket — they just don't belong as body prose. Each has a correct home: a dedicated section, a Jira field, or a linked artifact.

🗣 Raw Slack / meeting transcripts
The only true "don't." Pasting raw discussion buries the signal. Distill the decisions into the relevant sections; if the source matters, link it.
Distill into sections + link the source
🔮 Future enhancement ideas
Don't write full specs for later work here. But naming what's not in scope is good — it prevents scope creep. Keep it to a short bullet list with links to follow-up tickets.
"Out of Scope" section + linked follow-up tickets
⚙️ Micro implementation details
Don't pin volatile specifics — exact variable names, SQL syntax — that drift from code and rot. A pointer to the detailed design is welcome.
Link to design / tech-spec doc
📋 Deployment & rollback steps
Don't inline a full runbook in a story body. (A dedicated deployment ticket may legitimately carry these — depends on your team's flow.)
Runbook doc / deploy ticket — linked
📈 Post-launch monitoring
Don't inline dashboards, alerts, and SLOs. Do keep the success metric in the Problem Statement when it defines "done."
Ops ticket / runbook — link dashboards
🔗 PR links & commit hashes
These are tracking data, not body prose — and they don't rot when handled right. Don't hand-maintain a list in the body; let the dev-panel integration populate them, or add as comments.
