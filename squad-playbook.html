R Responsible (does the work) · A Accountable (owns the outcome) · C Consulted · I Informed

Rotation: the Three Amigos dev + tester rotate each sprint (round-robin from a posted list), and facilitation rotates with them — so no single person becomes the new bottleneck. Escalate to the lead only when triage can't resolve feasibility, two artifacts conflict, or priority/scope is contested. Day-to-day framing does not route through the lead.

2 Definition of Ready & Done

The human-runnable gates. These are checklists a person ticks — no tooling required (an agent can pre-check them, see §5).

✓ Definition of Ready (story → sprint)

  • Story links to its parent PRD/Epic requirement(s)
  • Every requirement it claims has a solves: to a problem
  • Every AC is observable & testable
  • Every requirement slice is covered by ≥1 AC (no gaps)
  • Every AC has ≥1 test scenario in the Test Plan
  • Impl Plan exists; blockers/open questions surfaced
  • Estimated (async) by dev + tester

✓ Definition of Done (story → closed)

  • All AC demonstrably met
  • All Test Plan scenarios pass (incl. edge/error)
  • Code reviewed & approved
  • No requirement left partially covered
  • Follow-ups / deferred items linked as tickets
  • Success metric instrumented if this story defines it

3 Lightweight path — not every ticket gets full framing

Full P→R→AC framing is for user-facing change. Forcing it onto a 1-pointer or a chore is how a process gets abandoned. Match the ceremony to the ticket.

Rule of thumb: if a user could notice the change, it needs AC + a trace to a problem. If only the codebase notices, the enabler reason + a testable DoD is enough.

4 Async estimation & continuous refinement

~10% of capacity, ongoing. The live meeting is short and decision-only — estimation happens before it, asynchronously.

  1. Refinement-ready tickets are queued with a Jira label (e.g. needs-estimate) as soon as they pass §1 framing.
  2. Dev + tester estimate independently & async — drop a point value in a Jira comment (or a poll tool) within the refinement window. No meeting needed for agreement.
  3. Agreement → done. If estimates match (or are within one step), the ticket is sized; move on.
  4. Disagreement → the short live meeting. Only tickets where estimates diverge, or that raise a real question, go to the weekly 15–30 min decision-only session.
  5. Lead joins only on escalation — not as the default estimator.
Why async first: the old pain was one big batch meeting producing nominal estimates with no shared understanding. Per-ticket async estimation forces each estimator to actually read the framing — and shrinks the live meeting to the few items that genuinely need a conversation.

5 Agents are accelerators, not the process

The agent rail in the anatomy shows skills that can author (＋) and check (✓) each artifact. Treat them as optional speed-ups layered on top of a process that already works by hand.

Adopt manual-first. Every step in §1–4 is doable with the templates and the DoR/DoD checklists and no AI at all. That is deliberate: if a skill is missing, slow, or wrong, the squad is never blocked. Add agents one at a time, only after the manual step is a habit.

Known-available today: the jira-problem-framing skill decomposes a ticket into P→R→AC and reports coverage gaps (orphan/bare requirements, untestable ACs) — i.e. it can run the §2 DoR coverage check for you. The other skills shown in the anatomy (problem-distiller, requirement-slicer, impl-planner…) are aspirational until built — confirm before relying on them.
