Artifact Lifecycle — Stages & Their Documents

Each stage has one place it stores its outcome — PRP → Draft PRD → PRD → Story — and the PRD/Story are containers, not artifacts themselves. The Traceable artifacts (Problem, Requirements, Non-Goals, AC) generally just Form → Canonical, sometimes with an in-between Consumed block marking where they get sliced into the next container. The Build artifacts (Test Plan, Impl Plan, Code, Review) aren't part of that trace and follow whatever shape fits them. Companion to the ticket anatomy and the playbook.

How to read it. Follow a row left-to-right. Traceable artifacts end at Canonical (or one Consumed block after it); Build artifacts run their own course.
  • AC forms in the PRD, canonical in the Story. A draft AC is sketched per-requirement while the PRD is written (Design); it becomes final and testable once sliced into a Story (Refinement).
  • Non-Goals now mirror Requirements. Drafted in Triage alongside the requirements, canonical (epic-level) once the PRD is written, then simply sliced into the Story at Refinement — no separate "local" path.
  • Planning still touches no Traceable artifact. Cycle/sprint planning, task prioritization, resource allocation, timeline creation — none of it edits a Problem, Requirement, Non-Goal, or AC. But it's no longer blank for everything: the moment a ticket is pulled into a sprint, an AI agent can draft the Test Plan and Implementation Plan straight from the now-canonical AC.
  • Solutioning is where that draft becomes canonical. A dev/tester picks up the AI draft and finalizes it before code starts. Implementation then builds from the finalized plans — shown as Code's own "Forms" step, not a repeated marker on the plans' rows.
Notes: Build artifacts deliberately don't follow the Traceable pattern. Per spec-driven development, the Implementation Plan is kept alive alongside the code rather than discarded the moment it's written — it's updated through QA as review feedback changes the code, and only goes Done at Deployment, together with Code, not one stage earlier. Test Plan still closes at QA, once its scenarios are actually executed — that's a real, different closing event. Separately, the AI-draft-on-sprint-pull step assumes an agent capable of turning canonical AC into a draft plan — same caveat as the agent rail in the ticket anatomy: verify it exists (or get it built) before relying on it.
